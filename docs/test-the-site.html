Help test Plebum Dominium

Before you begin

Choose one check or give website feedback. Follow its instructions and report what happened—even if it fails or you cannot finish.

Testing only, not approved for real-wallet use. Use public fixtures and disposable inputs. Never use or submit real seed phrases, private keys, passwords, wallet backups, personal financial data, or funds. Never bypass an offline safeguard that remains blocked.

For tool checks: prepare the files before disconnecting. Website feedback needs no downloads.

  1. Download the public tester ZIP, then read the included README.txt and TESTING.txt. Record the release ID: alpha-20261106-t3-t4. See all download options.
  2. Verify package checksums before running any tools. Use the complete offline / website-tools ZIP checksums or the focused dice/map ZIP checksums for the package you downloaded. A matching hash checks consistency, not software safety or publisher authenticity.
  3. Extract the entire ZIP and find the test folder. For the complete offline or website-tools ZIP, open plebum-offline, then START.html. For T2–T5, open public-tests inside that folder; its test inputs are in plebum-offline/public-tests/fixtures/. For the focused dice/map ZIP, open plebum-public-test; tools and fixtures are directly inside it. Use the matching HTML/Python tools beside fixtures, and open your terminal in that test folder for the commands in TESTING.txt. See the illustrated folder guide.
  4. Use the downloaded public alpha on a disconnected test machine, with public fixtures only. Choose one of the five verification tracks below; the physical Tails track requires real Tails hardware.

Choose one verification track

Report each track separately in the feedback form. For each check: PASS means completed successfully; FAIL means an observed mismatch; NOT TESTED means skipped or incomplete. A whole track passes only when every required check was completed and passed.

T1 · Package integrity

Before extracting: use Select ZIP to verify to compare your downloaded archive with its published SHA-256 checksum. This quick check keeps the file on your device. Continue with the extracted-file checks below to complete T1.

Do: Run the included Python 3 package verification script and check every listed file against the provided checksums. For the complete offline or website-tools ZIP, open a terminal in plebum-offline and run python3 verify_package.py (Windows: py verify_package.py) to check the whole package. The separate checker inside public-tests checks only the focused test subset. For the focused dice/map ZIP, run the checker from plebum-public-test.

Report: Which package you checked, whether the script ran, whether every file passed, and any missing or mismatched files. Stop and report a mismatch before continuing.

Instructions · T1

  1. Before extracting, compare the ZIP with its published checksum using the download verifier linked above.
  2. Extract the entire package. For a complete offline or website-tools ZIP, open a terminal in plebum-offline. For a focused ZIP, use plebum-public-test.
  3. Run python3 verify_package.py (Windows: py verify_package.py). Every listed file must pass. The checker in public-tests checks only that subset, not the complete offline package.
  4. Record the package filename, ZIP hash, file count and output. Stop on any missing file or checksum mismatch.
T2 · Local and offline safeguards

Do: Check that sensitive operations are blocked when connected; disconnect using OS network controls and try only the supplied public fixtures; reconnect and check the safeguards again.

Report: Connected-state blocking, permitted offline fixture behavior, and the response to reconnection. Do not override a blocked state.

Instructions · T2

  1. While connected, open the extracted local HTML dice and wallet-map tools without entering any data. Sensitive operations must be blocked.
  2. Close them, disable networking with OS controls, and reopen the local files. Use only the supplied public fixtures. Record whether offline operation is permitted; if it remains blocked, report it without bypassing the control.
  3. After a public-fixture operation, reconnect. Sensitive controls must block and stale output must clear. Record each tool separately.

The browser offline indicator does not prove network isolation. The Python wallet-map tool gives an offline notice; it does not detect networking.

T3 · Dice converter known-answer tests

Do: Compare the HTML and Python tools against the published all-zero and all-one fixtures, reject a 255-bit input and an input containing x, and check the eight additional BIP39 reference vectors.

Report: Each expected-versus-actual result, including any disagreement between implementations. Never use fixture-derived mnemonics for real funds.

Instructions · T3

  1. Offline, open the local dice converter. Paste fixtures/zeros-256.txt into its binary-input box. Expected: abandon repeated 23 times, then art. Repeat in bip39_dice_converter.py; outputs must match.
  2. Repeat with fixtures/ones-256.txt. Expected: zoo repeated 23 times, then vote.
  3. Try 255 bits and a string containing x. Both must be rejected without valid output.
  4. Check all eight pairs in fixtures/bip39-vectors.json in both tools. Convert each hex entropy value to exactly 256 binary digits, preserving leading zeroes.
  5. Repeat the manual dice-entry/button interaction on this candidate and record any remaining input problem.
T4 · Wallet-map encryption and decryption

Do: Test an exact round trip with public text including Unicode and line breaks; reject a wrong password and truncated ciphertext; test HTML-to-Python and Python-to-HTML interoperability.

Report: Whether the original text was recovered byte-for-byte and which negative or cross-tool checks passed or failed. Use disposable passwords and public text only.

Instructions · T4

Follow the step-by-step T4 retest instructions, exact commands and byte comparisons (TXT). Install Python 3 and GnuPG before disconnecting. Use matching candidate HTML/Python files.

  1. T4.1: load fixtures/public-map.txt with the file picker, encrypt with disposable password public-test-only, save, close/reopen, decrypt and download the restored text. Compare file bytes, including the final newline; visual similarity is insufficient.
  2. T4.2: decrypt a copy with a wrong password. Expect an error with no plaintext or plaintext download.
  3. T4.3: truncate a copy of the ciphertext and try decrypting. Expect rejection with no plaintext. Preserve the undamaged original.
  4. T4.4: test both directions: browser encrypts → Python decrypts; Python encrypts → browser decrypts. Compare restored bytes in each direction. Use new output filenames because Python refuses overwrites.
  5. Repeat T2 reconnection clearing on this candidate. Report every subcheck separately; a partial result does not close T4.

These commands use public-test-only; the general TESTING.txt fixture exercise uses the separate password in fixtures/password.txt. Follow the password for the exercise you chose.

T5 · Physical Tails verification

Do: On actual Tails hardware, confirm an offline boot, local HTML operation, T2 safeguards, T3 conversion, T4 encryption, and restart/reboot behavior.

Report: Tails version, hardware, which checks were completed, any dependency or file-retention problems, and what happened after reboot. This track requires physical hardware; mark it NOT TESTED otherwise.

Instructions · T5

  1. Prepare the complete extracted package and required dependencies before disconnecting. Record Tails version, hardware, browser, Python and GnuPG versions.
  2. Boot actual Tails hardware with networking disabled and confirm the OS network state. A phone or simulated browser session cannot complete T5.
  3. Open the extracted local HTML tools and repeat T2, T3 and T4 with public fixtures. Record browser restrictions, missing dependencies and each subcheck.
  4. Close the tools, shut down and reboot. Check which test files remain on the removable drive and whether local tools restart correctly. Do not infer secure erasure from a reboot.
  5. Report hardware, versions, results and limitations. Mark anything unperformed NOT TESTED. Full wallet setup, signing and recovery are separate beta checks below.
General website feedback

No technical experience needed. Review instructions, links, path switching, mobile layout, keyboard access, search, download labels and clarity. Report broken links, confusing language, missing prerequisites, accessibility problems or suggestions.

In the form select General website feedback, then choose the affected area, feedback type and severity. Include the exact page URL and steps to reproduce when possible. This route is separate from T1–T5.

How to submit a useful report

  1. Finish one task or clearly mark checks you could not perform NOT TESTED.
  2. After your offline session, reconnect only when safe to do so and open the public feedback form.
  3. Select T1, T2, T3, T4, T5 or General website feedback. The form will show the matching questions.
  4. Enter the release ID alpha-20261106-t3-t4 (or your actual package filename), overall result, and a factual description of the observed outcome.
  5. Where possible, include operating system, browser, Python/GnuPG versions, Tails hardware, reproducible steps, expected versus actual results, and non-sensitive hashes. Submit one report per track or issue.

Never submit secrets. Contact information is optional; the form does not require file uploads. Remove personal data from any evidence you choose to share.

What must be checked before beta

All five tool tracks need complete passing evidence for the proposed beta package in the supported environments. The following guide modules and release checks also need completion. T5 alone does not complete the guide's wallet rehearsals.

  1. Downloads, file verification and offline preparation — T1, T2 and T5. Follow Check the files and Two boots. Verify the complete package, local operation, connected-state blocking and reconnection clearing in actual browsers/OSes and physical Tails.
  2. Key generation and passphrase tools — T3 and T5. Test one-key generation, three-key generation and the passphrase/Diceware steps with public fixtures. Confirm expected outputs, rejected inputs, manual entry and matching HTML/Python results.
  3. Wallet-map protection — T4 and T5. Test Protect the wallet map: exact saved-file restoration, wrong-password/damaged-file rejection, both interoperability directions, Windows and actual Tails.
  4. One key + passphrase — complete rehearsal outstanding. Follow the wallet setup, signing and recovery instructions with disposable test-only records. Verify the wallet configuration and addresses, a signing rehearsal, restoration using the seed plus exact passphrase, and wrong/missing-passphrase outcomes.
  5. Three keys / 2-of-3 — complete rehearsal outstanding. Test wallet construction, test-wallet setup and spending and recovery. Verify the full policy, signer pairs, transaction review and recovery with one unavailable key using the complete wallet configuration. Any transaction rehearsal must stay on the guide's designated test network with disposable keys; no real funds.
  6. Backups, inheritance and recovery cards — both paths. Rehearse from copies of disposable records: one-key backups, three-key backups, one-key inheritance, three-key inheritance, and each path's recovery card. Confirm another reader can identify every required record without relying on the original device. Preserve original test records.
  7. Whole-guide usability and release consistency. Complete both routes on desktop/mobile; check keyboard access, path switching, search, links, light/dark mode, print and extracted offline navigation. Reconcile legacy PDFs/instructions with the current guide, resolve blocking findings, then rebuild and recheck the final ZIPs, manifests and hashes together.

Evidence needed: package filename and hash, module/track, OS/browser or Tails hardware and versions, each required result, expected versus actual behavior, and reproducible non-sensitive evidence. Use PASS, FAIL or NOT TESTED; unresolved failures and missing required evidence keep the beta gate open.

After review of those results, the maintainer can decide whether to designate a beta. Beta remains a testing stage and does not itself approve real-wallet custody or relaunch production.

What these results mean

Reports help us reproduce failures, prioritize safety concerns and identify untested environments. A PASS report is useful evidence, but it does not certify a release. Physical Tails, browser isolation, offline controls and recovery validation remain subject to independent review. This public alpha is for testing only, not real wallet secrets or funds.
