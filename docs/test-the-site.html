Help test Plebum Dominium

Plebum Dominium teaches self-custody without a hardware wallet. Create and verify keys with offline software, put the backups on metal, and check that they restore the intended wallet. Use offline software to sign. Hardware wallets are optional signing tools introduced only after the metal backups are complete and checked. Public-alpha rehearsals use only disposable data and the designated test network. Record software signing and recovery separately from optional hardware tests. Paper practice does not pass metal checks. T5 alone does not establish beta readiness.

Before you begin

Choose one test. Follow the steps, save the result, then move on. Website feedback needs no downloads.

Public testing only. Use the supplied examples and disposable test passwords. Never use or submit real wallet secrets, backups or funds.

  1. Prepare online. Download a complete offline or tools-only tester ZIP, or the focused tool ZIP, with its matching checksums. Save the download verifier separately if you need it offline. Check Python 3 and GnuPG before disconnecting if testing the Python map tool.
  2. Copy to your test USB. Use a data USB separate from the Tails boot USB. Copy the ZIP, checksums, saved verifier and the entire extracted folder. Open the copied files to check them. No formatting or overwriting the boot stick is needed.
  3. Find the test folder. Complete/tools-only ZIP: open plebum-offline/START.html; the T2–T5 tools are in plebum-offline/public-tests. Focused ZIP: open plebum-public-test. The fixtures folder is beside the matching tools. Open your terminal there for the test commands. Illustrated folder guide →
  4. Make somewhere to save. Create results in the test folder. Copy SESSION-NOTES.txt and RESULTS.csv there before editing; leave packaged originals intact. On the data USB, create a folder such as Plebum-test-evidence/2026-11-08-Tails-r4/ for screenshots and notes. Keep Windows and Tails evidence separate.
  5. Start offline. Disable OS networking and disconnect network cables. In Tails choose Offline Mode → Disable all networking at startup and check the OS controls. Keep networking disabled. A browser flag or “disconnected” label alone does not establish isolation.

Already tested with us? Keep those results with their original package and date. r4 refreshes instructions; the tool code matches r3. Check the new ZIP with T1, then use the short remaining retest. You do not need to repeat all eight earlier vectors or the reboot just to refresh evidence.

How to save screenshots as you test

Save after each result, before clearing or trying the next input. Include the case/file name and readable output. If a check fails, capture the error before retrying and keep the failed result.

  • Windows: press Win + Shift + S, capture, then open the capture and Save as into your evidence folder.
  • Tails: press Print/PrtSc (possibly with Fn), select the window or area, and capture. Check Home → Pictures → Screenshots. Open the image, name it for the checkpoint, and copy it to the data USB.
  • Keep the original .png files. A readable phone photo is acceptable; a short recording can show button or clearing behavior. Use public data only and keep unrelated private windows out of view.

A clipboard capture is not a saved file. Files left only in Tails Home should not be assumed to survive shutdown.

Before you pause, reboot or shut down

  1. Save the results. Record completed and unfinished checks. Copy screenshots from Pictures/Screenshots, your notes, terminal output, public .asc/.txt files and any before-reboot checksum file to the data USB. Keep the extracted package with its results folder.
  2. Check the copy. Wait for copying to finish. Open the USB again in Files and check its drive label/path. Confirm each file listed in your notes is there. Open an actual saved PNG and text result from the USB and read them; a folder screenshot alone is not enough.
  3. Finish cleanly. Save the last completed and next step. Lock and clear the tools, close apps and terminals using the data USB, then eject that data USB and wait for safe removal. Shut down Tails through the Power Off menu and confirm. Remove the boot USB only after the computer is off.

  4. One key + passphrase — complete rehearsal outstanding. Follow the wallet setup, signing and recovery instructions with disposable test-only records. Verify the wallet configuration and addresses, a signing rehearsal, restoration using the seed plus exact passphrase, and wrong/missing-passphrase outcomes.
  5. Three keys / 2-of-3 — complete rehearsal outstanding. Test wallet construction, test-wallet setup and spending and recovery. Verify the full policy, signer pairs, transaction review and recovery with one unavailable key using the complete wallet configuration. Any transaction rehearsal must stay on the guide's designated test network with disposable keys; no real funds.
  6. Backups, inheritance and recovery cards — both paths. Rehearse from copies of disposable records: one-key backups, three-key backups, one-key inheritance, three-key inheritance, and each path's recovery card. Confirm another reader can identify every required record without relying on the original device. Preserve original test records.
  7. Whole-guide usability and release consistency. Complete both routes on desktop/mobile; check keyboard access, path switching, search, links, light/dark mode, print and extracted offline navigation. Reconcile legacy PDFs/instructions with the current guide, resolve blocking findings, then rebuild and recheck the final ZIPs, manifests and hashes together.

Evidence needed: package filename and hash, module/track, OS/browser or Tails hardware and versions, each required result, expected versus actual behavior, and reproducible non-sensitive evidence. Use PASS, FAIL or NOT TESTED; unresolved failures and missing required evidence keep the beta gate open.

After review of those results, the maintainer can decide whether to designate a beta. Beta remains a testing stage and does not itself approve real-wallet custody or relaunch production.

What these results mean

Reports help us reproduce failures, prioritize safety concerns and identify untested environments. A PASS report is useful evidence, but it does not certify a release. Physical Tails, browser isolation, offline controls and recovery validation remain subject to independent review. This public alpha is for testing only, not real wallet secrets or funds.

Test it together, one step at a time

Show the setup screen, say what you expected, then show what happened. A screenshot, short video or written observation can support a result. Label each file with the test step, date, software version and package hash. Mark a step PASS only when it was actually performed and the expected result has evidence. Mark a mismatch FAIL and an unperformed check NOT TESTED. Reading a page or watching a demo is an instructional check, not hands-on wallet verification.

On Tails, press PrtScn or choose Take Screenshot in the system menu. Select screenshot or screencast mode. Screenshots go to Pictures; videos go to Videos and have no sound. Test capture with a harmless screen first. Save reviewed evidence to a separate evidence USB before shutting down, since unsaved session files are lost.

Stop recording before creating, entering or restoring secrets. Keep seed words, passphrases, private keys, QR secrets and engraved plates out of every frame. Resume only on public test-wallet details and results. Use a written witness note for the private step. Do not reconnect a secret-bearing Tails session to upload evidence; shut down fully first.
