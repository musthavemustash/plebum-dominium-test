CHECKPOINT 2 / 3

Make sure the signature
belongs to the right key.

Use the publisher’s public verification key. This is separate from your wallet keys: file verification never needs your seed words or private keys. Establish whose key you expect, then check what it signed.

  1. 1Follow the publisher’s documented process to confirm the signing key’s full fingerprint using an independently trusted source.
  2. 2Use the project’s verifier or documented signature commands for the exact release.
  3. 3Confirm the signature covers your download directly, or the checksum list that names your file.
What this establishesA valid signature connects the signed content to the authenticated signing key. It does not audit the program’s code.

CHECKPOINT 3 / 3

Compare your file
with the expected hash.

A SHA-256 hash is a 64-character digest of a file’s contents. Calculate yours and compare all 64 characters with the authenticated reference for that exact file.

Get-FileHash -LiteralPath ".\example-app.zip" -Algorithm SHA256 | Format-List
PowerShell · run in the file’s folder, or use its full path
What a match meansYour file matches the referenced bytes. If the reference itself is unauthenticated, a match alone does not establish who published the file.

If the publisher signs the download directly, follow its documented direct-signature process. A separate checksum list may not be required.

What if a signature checker reports an untrusted key?

A valid signature and local key-trust settings answer different questions. “Not certified” may reflect your local trust configuration, but you still need to independently establish the key’s identity. Investigate an unexpected key, bad signature, or unresolved warning.
