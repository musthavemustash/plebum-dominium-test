Check the files

You will need: The downloaded files · Two verification tools

Verify the file, its source, and the signing key before running it.

Staging guide: a familiar domain or HTTPS connection does not certify software safety. This site’s tools and instructions remain under review. Never enter signing secrets into the live website.

1 · Source

Start with the project

Use the developer’s official download and verification instructions for the exact release and operating system. Avoid links from advertisements, unsolicited messages, or search-result lookalikes.

For this kit, the downloads page and manifest identify distributed files. They do not independently audit their code.

What HTTPS tells you

HTTPS protects the connection to the named domain. It does not prove that the domain, its publisher, or the downloaded program is trustworthy.

2 · Integrity

Compare the complete hash

Calculate the downloaded file’s SHA-256 digest and compare every character with the authenticated expected value for that exact release. The file checker can compare a kit file with its listed digest.

A match means the bytes agree with the reference. If an attacker replaces both the file and the reference, that comparison will still pass.

Command-line alternatives

On macOS, use shasum -a 256 followed by the file path. In Windows PowerShell, use Get-FileHash -Algorithm SHA256 with the file path. Follow the project’s instructions for your platform.

3 · Authenticity

Verify the signer, then the signature

Where the publisher provides signatures, authenticate the signing key’s full fingerprint using the publisher’s documented verification process and an independently trusted source. Then verify the signature for the exact downloaded file or signed checksum manifest.

“Good signature” alone is insufficient. It means the signature verifies under a key; you must establish whose key it is. A new key or unexplained fingerprint change needs investigation.

About trust warnings

A message that a key is not certified can reflect your local trust settings. Do not dismiss it without independently checking the key identity. Stop for a bad signature, unexpected key, or unresolved warning.

4 · Ready to proceed?

Keep a verification record

Record the release, file name, hash, verification method, and signing-key fingerprint when applicable. Run any kit verification script only after reviewing and authenticating that script too.

Never run a failed or unexplained download. Recheck the source and release before trying again. A successful checksum or signature does not establish that software is bug-free or appropriate for custody.

Stop if: the source is uncertain, a hash differs, a signature fails, the key identity is unverified, or the release cannot be matched to its verification instructions. Do not proceed to secret-handling work.

Use the current official instructions: Tails installation · Sparrow downloads and verification.
